# Как участвовать

Спасибо за интерес к проекту. Ниже — всё, что нужно знать, чтобы изменения
прошли ревью с первого раза.

## Подготовка окружения

```bash
git clone https://github.com/ArtVsMark/Glossary-Python.git
cd Glossary-Python
make install     # venv, пакет в режиме разработки, dev-зависимости, pre-commit
```

`make install` ставит pre-commit-хуки: перед каждым коммитом прогоняются ruff,
mypy, валидация данных и проверка синхронности витрины. Полный набор проверок
(тот же, что в CI) — `make check`.

## Главное правило

**Содержание глоссария правится в `data/cards/`.** Карточки лежат по файлу на
цветовую группу; `data/glossary.json` собирается из них, а `python_glossary.html`
— из сборки. Оба файла производные: правка в них живёт до первой сборки.

```
data/cards/*.json ──► data/glossary.json ──► python_glossary.html
 (правится здесь)        (сборка)               (витрина)
```

Stepik-Python-Grader получает итоговое содержимое выгрузкой и сам карточки не
правит: одна и та же карточка в двух местах разъезжается на первой же
синхронизации.

## Что делать с ошибкой в карточке

Править в `data/cards/<группа>.json`, затем `make assemble`. Валидатор уже
считает такие находки, и отчёт показывает, с чего начать:

```bash
make objections            # отчёт: правило, сколько карточек, какие именно
make objections --limit 0  # полный список, когда его будут разбирать целиком
```

Если нужного правила в валидаторе нет — заведите его: одна функция в
`src/glossary/validation.py` и строка в `RULES`. Так дефект становится
списком карточек, а не словами, и его возврат ловится автоматически.
Содержание и инструменты едут отдельными изменениями.

## Сборка

```bash
make assemble                                            # data/cards/ → data/glossary.json
make validate                                            # проверить качество
make build                                               # пересобрать витрину
git add data/cards data/glossary.json python_glossary.html
```

Сборка идемпотентна: один и тот же вход даёт побайтово одинаковый файл. В него
попадают карточки со статусом `ready`, порядок — раздел, затем `id`.
`make assemble-check` сверяет сборку с карточками, ничего не записывая.
Группа карточки задаётся именем файла, в самой карточке поля `color_group` нет.

### Поля карточки

Форма унаследована от базы знаний грейдера, откуда карточки переехали, и
совпадает с тем, что грейдер читает: выгрузка не требует преобразования схемы.
Полное описание — в `data/glossary.schema.json`.

| Поле | Требование |
| --- | --- |
| `id` | Уникальный, без пробелов и символов `#/?&=%"'<>` — используется как якорь URL |
| `title` | `{ru, en}`, отображаемое имя: `str.strip()`, `ValueError`, `match`. Имя из кода не переводится — половины совпадают |
| `kind` | `term`, `function`, `exception` или `construct` |
| `summary` | `{ru, en}`, 30–200 символов: помещается в список без раскрытия |
| `body` | `{ru, en}`, развёрнутый разбор от 60 символов |
| `section` | Раздел — ключ навигации; подписи на двух языках задаёт `glossary/taxonomy.py` |
| `subcat` | `{ru, en}`, подкатегория внутри раздела |
| `color_group` | Одна из десяти групп; задана именем файла в `data/cards/` |
| `aliases` / `keywords` | Синонимы и ключевые слова — по ним работает поиск |
| `examples` | Самостоятельные примеры: массив блоков, блок — массив строк кода с результатом в комментариях `# →`. Каждый блок исполняется сам по себе — импорты и определения, которые ему нужны, пишутся в нём же |
| `related` / `related_errors` | Идентификаторы существующих карточек |
| `added` | С какой версии есть: `N.N`; `<3.0` — появилось ещё в Python 2; `3.0` — пришло с Python 3 |
| `deprecated` | С какой версии устарело: `N.N` либо пустая строка |
| `removed` | В какой версии удалено или будет удалено — до какой работает: `N.N` либо пустая строка |
| `platforms` | `["AllOS"]` — везде; иначе подмножество `Linux`, `macOS`, `Windows`. По директиве `availability` документации: Unix и POSIX — `Linux` и `macOS` |
| `docs_url` | Конкретный раздел или якорь на docs.python.org, не корень |

### Храповик качества

`tests/quality_baseline.json` фиксирует, сколько предупреждений допустимо по
каждому правилу. Тест не даёт этому числу расти. Опустить планку можно только
после правки карточек в `data/cards/` — если правка **уменьшила** количество
замечаний, тест упадёт с подсказкой, какое именно число опустить.
Это осознанный шаг: качество данных двигается только в одну сторону.

## Правка кода

- Python 3.14+ — планка проекта; код пакета разбирается и младшей версией замера
  языка (матрица `inventory` в `badges.yml`, держит `tests/test_measured_versions.py`).
  Аннотации типов обязательны, mypy в строгом режиме.
- Docstring — на модуль, публичный класс и публичную функцию; стиль Google.
- Комментарий объясняет «почему», а не «что»: «что» должно быть видно из кода.
- Новое поведение сопровождается тестом. Покрытие в CI не ниже 90 %.
- Форматирование и импорты — ruff (`make format`), вручную ничего править
  не нужно.
- Починка называет соседние случаи — те, что решаются тем же признаком, — и
  отвечает по каждому: работал ли он прежде и работает ли теперь. «Соседей
  нет» произносится, а не подразумевается (правило каталога 195).
- Вторая находка по одному месту — предикату, разбору, ветвлению —
  останавливает починку по одной форме: сначала перечень форм с замером, и на
  каждую проверка, потом правка (правило 210).

### Запись в журнал изменений

Ни одной строки в `CHANGELOG.md` руками. Запись приезжает **отдельным файлом**:

```
changelog.d/<slug>.<секция>.md
```

Внутри — одна строка, без ведущего дефиса. Секции: `added`, `changed`,
`fixed`, `removed`, `internal`. Подробности — в
[`changelog.d/README.md`](changelog.d/README.md).

Два файла с разными именами не конфликтуют никогда. Общий файл конфликтует на
каждом параллельном изменении, а конфликтное изменение остаётся **вовсе без
проверок**: прогон идёт по merge-коммиту, которого при конфликте не существует.

```bash
make changelog-check     # форма записей
make changelog-preview   # как соберётся
```

### Числа в документации

Ни одной цифры в README руками. Число живёт внутри именованного маркера и
переписывается сборкой:

```markdown
**<!--m:cards-->581<!--/m:cards--> карточка**
```

```bash
make facts        # пересчитать и переписать
make facts-check  # проверить, что не разъехалось
```

Гейт падает и когда значение устарело, и когда маркер удалили: без третьего
условия механизма нет, есть ручное число с лишним шагом. Новое число —
это ключ в `marker_values()` из `scripts/facts.py` и маркер в README.

### Ссылки в документации

Битую ссылку между документами ловит гейт, а не читатель:

```bash
make links   # тот же шаг, что в CI
```

Цель ищется **разметкой** — `](адрес` и `]: адрес`, — а не вхождением адреса
в текст. Разница не косметическая: подстрока находится в подписи, поэтому
`[docs/architecture.md](никуда.md)` проходит проверку подстрокой зелёной и
ведёт в никуда.

Чего гейт не ловит, названо в докстринге `scripts/check_links.py`: внешние
`https://`-адреса не запрашиваются (сетевой шаг был бы недетерминирован),
якорь `#раздел` не разрешается, код гасится. Предмет — список `DOCUMENTS`
в том же файле; новый документ добавляется в него явно.

### Как добавить правило валидации

1. Напишите функцию в `src/glossary/validation.py` с сигнатурой
   `(Glossary, ValidationConfig) -> Iterator[Issue]`.
2. Добавьте её в кортеж `RULES`.
3. Пороговые значения, если они есть, вынесите в `ValidationConfig`.
4. Покройте тестами оба исхода — срабатывание и его отсутствие.
5. Если правило находит замечания в текущих данных, внесите их количество
   в `tests/quality_baseline.json` и опишите правило в таблице README.

Новое правило вводится как предупреждение. Ошибкой оно становится тогда, когда
данные ему полностью соответствуют — иначе ветка `main` окажется красной.

### Как добавить формат экспорта

1. Создайте класс в `src/glossary/exporters/` с атрибутами `name`, `suffix`
   и методом `render(glossary) -> str`. Работа с файловой системой остаётся
   вызывающему коду.
2. Зарегистрируйте класс в `_FACTORIES` в `exporters/__init__.py` — CLI подхватит
   формат автоматически.
3. Параметризованный тест `test_every_registered_format_renders` покроет базовый
   контракт; добавьте тесты на специфику формата.

## Оформление коммитов и pull request

Коммиты — в стиле [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
feat(export): добавить экспорт в Anki
fix(cli): корректный код возврата при отсутствии витрины
data: уточнить описания карточек модуля logging
docs: описать процесс добавления правил валидации
```

Перед отправкой PR:

```bash
make check
```

В описании PR заполните шаблон и укажите, что именно проверяли. PR с красным CI
не рассматривается.

Числа, перечни и «что тронуто» в теле PR и во фрагменте журнала снимаются
командой в момент записи — `git diff --stat origin/main`, вывод `make check`, —
а не вспоминаются, и команда названа рядом (правило каталога 215).

## Куда писать

- Новая карточка или правка содержимого — issue по соответствующему шаблону.
- Ошибка в инструментах или витрине — шаблон «Ошибка в инструментах».
- Вопросы и идеи по развитию — Discussions.
