# Архитектура

Документ фиксирует принятые решения и их цену. Он нужен, чтобы через полгода
не пересматривать одно и то же по второму разу.

## Общая картина

```
Stepik-Python-Grader
   (база знаний)
        │  import_from_grader.py
        ▼
data/glossary.json ──► loader ──► Glossary ──┬─► validation ──┬─► отчёт / коды возврата
      (снимок)                               │                └─► objections ──┐
                                             └─► exporters ──┬─► HTML-витрина  │
                                                             ├─► JSON          │
                                                             ├─► Markdown      │
                                                             └─► CSV           │
        ┌────────────────────────────────────────────────────────────────────┘
        ▼
Stepik-Python-Grader (issue с замечаниями к содержанию)
```

Поток содержания односторонний: данные читаются, проверяются, отдаются наружу.
Назад возвращаются только замечания — отчётом, а не правкой. Модели неизменяемы
(`frozen=True, slots=True`), поэтому экспортёры не могут разойтись в трактовке
одних и тех же карточек.

## Принятые решения

### Данные отделены от представления

**Было.** Единственный артефакт — `python_glossary.html` на 599 строк, внутри
которого CSS, JavaScript и JSON с карточками одной строкой длиной 532 КБ.

**Стало.** `data/glossary.json` — отдельный файл данных, HTML собирается из него.

**Зачем.** Данные стали пригодны к автоматической проверке, экспорту и переносу
между проектами; diff в git отражает смысловые правки, а не сдвиг байтов внутри
одной гигантской строки.

**Цена.** Появился шаг сборки. Он закрыт командой `glossary build --check`
в CI и pre-commit-хуке, поэтому забыть о нём нельзя.

### У содержания один хозяин, и он в другом репозитории

**Было.** Витрина была источником истины: карточки правились здесь, а грейдер
брал их одноразовым импортом из встроенного в HTML JSON.

**Стало.** Источник — база знаний `ArtVsMark/Stepik-Python-Grader`. Здесь лежит
её снимок, который перечитывается `scripts/import_from_grader.py`. Обратного
потока содержания нет.

**Зачем.** После того одноразового импорта глоссарий в грейдере ушёл далеко
вперёд: 1349 готовых карточек против 581 здесь, двуязычные тексты, синонимы,
связи. Две живые копии одних и тех же карточек разъезжаются на первой же
выгрузке, и спор о том, чья версия верна, решать некому — арбитра нет.
Односторонний поток снимает вопрос вместе с необходимостью в арбитре.

**Цена.** Ошибку в карточке нельзя починить на месте — её приходится
предъявлять источнику и ждать. Чтобы это не превращалось в «мы вроде говорили»,
замечания собираются командой `glossary objections` в готовый к отправке
список: правило, сколько карточек задето, какие именно. Правило валидации
здесь — это форма возражения, а не запрет.

### Форма карточки повторяет форму источника

Схема v2 приняла поля источника как есть: `title`, `kind`, двуязычные
`summary`/`body`, `aliases`, `keywords`, `related`.

**Зачем.** Своя третья форма означала бы отображение в обе стороны и разъезд
на первом же новом поле источника.

**Исключение — `color_group`.** В источнике верхнеуровневая рубрика выражена
не полем, а раскладкой по файлам (`builtin.json`, `exc.json`, `str.json`).
Склейка 11 файлов в один снимок эту границу стирает, поэтому импорт переносит
имя файла в поле карточки. Выводить цвет из тегов не выйдет: теги тематические
(`os`, `bytearray`, `collections`) и группу не называют — на реальных данных
такой вывод промахивался на 667 карточках из 1349.

**Цена.** Появление нового файла в источнике — это незнакомая цветовая группа
здесь. Правило `color-group` поднимает такое ошибкой, а не подставляет цвет
по умолчанию: молча слитая с чужой рубрикой карточка выглядит исправной.

### Витрина собирается подстановкой, а не шаблонизатором

Шаблон `src/glossary/templates/showcase.html` — это исходная страница, в которой
блок данных заменён на `{{GLOSSARY_DATA}}`.

**Зачем.** Точка подстановки ровно одна. Jinja2 добавил бы зависимость, новый
синтаксис и риск случайного экранирования — ради одной операции `str.replace`.
Шаблон остаётся валидным HTML: его можно открыть в браузере и править в любом
редакторе.

**Цена.** Логика витрины (поиск, фильтры, переключение языка, подсветка,
скачивание страницы) живёт в JavaScript внутри шаблона и Python-тестами не
покрыта. Поведение перестало быть тривиальным — это записано в технический долг
как задача на браузерные тесты.

### Страница умеет сохранять сама себя

Кнопка «Скачать» отдаёт не текущий DOM, а копию исходной разметки, снятую
до того, как скрипт что-либо в ней изменил.

**Зачем.** Витрину скачивают, чтобы пользоваться офлайн. Сохранённый текущий
DOM принёс бы с собой чужой поисковый запрос, раскрытые карточки и чужую тему —
файл выглядел бы исправным и вёл себя странно. Снимок снимается один раз, и
копия копии побайтово совпадает с оригиналом.

**Цена.** Страница обязана оставаться самодостаточной: ни внешних шрифтов, ни
CDN, ни отложенной подгрузки. Отсюда системные шрифты вместо веб-шрифтов и
встроенный, а не подключаемый, JavaScript.

### Ноль runtime-зависимостей

Пакет использует только стандартную библиотеку: `json`, `csv`, `dataclasses`,
`argparse`, `importlib.resources`, `pathlib`.

**Зачем.** Инструмент запускается в любом окружении с Python 3.11+ — в минимальном
контейнере CI, на машине контрибьютора, из другого проекта. Нет цепочки
обновлений и уязвимостей в транзитивных зависимостях.

**Цена.** CLI на `argparse` многословнее, чем на Typer или Click. Для четырёх
команд разница не окупает зависимость.

### Валидация — реестр правил, а не один большой проход

Каждое правило — чистая функция `(Glossary, ValidationConfig) -> Iterator[Issue]`,
зарегистрированная в `RULES`.

**Зачем.** Новая проверка добавляется одной функцией и одной строкой; каждое
правило тестируется изолированно; отчёт можно фильтровать и агрегировать по
именам правил.

**Цена.** Каждое правило проходит по всем карточкам заново — десять проходов
вместо одного. На 581 карточке это доли миллисекунды; при росте на порядок
имеет смысл сгруппировать покарточные правила в один проход, сохранив внешний
контракт.

### Ошибки и предупреждения разделены

Ошибки ломают CI, предупреждения — нет.

**Зачем.** Данные достались проекту в готовом виде и содержат замечания, которые
нельзя устранить за один коммит. Если бы каждое замечание было ошибкой, ветка
`main` была бы красной с первого дня, и проверка перестала бы что-либо значить.

Механизм ужесточения: правило вводится как предупреждение → замечания
устраняются → правило переводится в ошибки. Порог движения контролирует храповик
`tests/quality_baseline.json`.

### Проект — модуль, а не хозяин данных

**Решение.** Содержание карточек приходит обработанным из
`ArtVsMark/Stepik-Python-Grader`. Здесь оно превращается в одну страницу,
которую скачивают и открывают; замечания к содержанию едут обратно в грейдер.

**Зачем.** У данных один хозяин. Правка карточки в двух местах разъезжается на
первой же выгрузке, а спор о том, чья версия верна, не имеет решения. Мы
потребитель и источник возражений — это разные роли, и обе названы в
[`docs/agent/roles.md`](agent/roles.md).

**Цена.** Свои улучшения контента мы не можем внести напрямую: они проходят
через грейдер. Взамен исчезает целый класс расхождений.

**Отвергнуто.** Вести содержание здесь и синхронизировать в обе стороны:
двусторонняя синхронизация требует разрешения конфликтов, для которого нет
арбитра.

### Ведущие роли — методист и дизайнер

**Решение.** Состав ролей строится вокруг двух: методиста и дизайнера.
Остальные роли существуют, потому что у продукта есть пласты, которые иначе
останутся без владельца.

**Зачем.** Проект существует ради того, чтобы обработанные данные читались и
запоминались **лучше, чем в источнике**. Если убрать методику и визуал,
останется экспорт JSON в HTML — а он уже есть и ценности не добавляет.

**Цена.** Две ведущие роли постоянно возражают друг другу: полнота против
читаемости. Это не дефект состава, а его смысл — роль, которая только
соглашается, не заводится (правило каталога 062).

## Текущий технический долг

| Что | Почему это долг | Когда разбирать |
| --- | --- | --- |
| 97 карточек: пример открывает блок без отступа | Код из глоссария не запускается | Предъявлено источнику (`example-indent`) |
| 309 карточек без развёрнутого тела | Карточка обрывается на сводке | Предъявлено источнику (`translated`) |
| 29 сводок вне диапазона 30–200 символов | Не помещается в список или ничего не объясняет | Предъявлено источнику (`summary-length`) |
| `section` и `subcat` одноязычны | В английском режиме витрина остаётся наполовину русской | Требует решения в источнике: поля должны стать `{ru, en}` |
| Раздел `Файлы и I_O` | Похоже на артефакт экранирования `I/O` | Предъявить источнику |
| Смешанные алфавиты в `id` (латиница и кириллица) | Не дефект, но конвенция не сформулирована | Требует решения |
| JavaScript витрины не покрыт тестами | Регрессия в поиске, языке или скачивании пройдёт незамеченной | Следующее изменение витрины |
| Витрина весит 2,7 МБ | Первая загрузка по мобильной сети заметна | При жалобах на скорость |
| Разность версий говорит «появилось в инвентаре», а читается как «появилось в языке» | `typing.Union` есть с 3.5, но в 3.14 стал классом — и попал в список нового | Названо в `scripts/whatsnew.py`; отделить «новое» от «изменившего природу» интроспекцией нельзя |

Первые три строки — не долг этого репозитория: содержание правится в источнике.
Здесь они держатся правилами валидации и храповиком, а предъявляются
командой `glossary objections`.

## Возможные направления

- **Автоматическая выгрузка.** Импорт есть и идемпотентен, но запускается
  руками из клона источника. Следующий шаг — регулярный прогон, открывающий
  pull request со свежим снимком.
- **Новые форматы экспорта.** Anki-колода, JSON Lines для индексации, вложения
  для LLM-ассистента. Реестр экспортёров рассчитан на такое расширение.
- **Двуязычие до конца.** Тексты карточек двуязычны, а названия разделов и
  подкатегорий — нет. Пока это не решено в источнике, английский режим витрины
  остаётся неполным.
- **Браузерные тесты витрины.** Поиск, переключение языка и скачивание страницы
  проверяются вручную. Playwright закрыл бы это без runtime-зависимостей
  в самом пакете.
