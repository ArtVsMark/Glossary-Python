# Архитектура

Документ фиксирует принятые решения и их цену. Он нужен, чтобы через полгода
не пересматривать одно и то же по второму разу.

## Общая картина

```
data/glossary.json ──► loader ──► Glossary ──┬─► validation ──► отчёт / коды возврата
   (источник истины)                         │
                                             └─► exporters ──┬─► HTML-витрина
                                                             ├─► JSON
                                                             ├─► Markdown
                                                             └─► CSV
```

Поток односторонний: данные читаются, проверяются, отдаются наружу. Модели
неизменяемы (`frozen=True, slots=True`), поэтому экспортёры не могут разойтись
в трактовке одних и тех же карточек.

## Принятые решения

### Данные отделены от представления

**Было.** Единственный артефакт — `python_glossary.html` на 599 строк, внутри
которого CSS, JavaScript и JSON с карточками одной строкой длиной 532 КБ.

**Стало.** `data/glossary.json` — источник истины, HTML собирается из него.

**Зачем.** Данные стали пригодны к автоматической проверке, экспорту и переносу
между проектами; diff в git отражает смысловые правки, а не сдвиг байтов внутри
одной гигантской строки.

**Цена.** Появился шаг сборки. Он закрыт командой `glossary build --check`
в CI и pre-commit-хуке, поэтому забыть о нём нельзя.

### Витрина собирается подстановкой, а не шаблонизатором

Шаблон `src/glossary/templates/showcase.html` — это исходная страница, в которой
блок данных заменён на `{{GLOSSARY_DATA}}`.

**Зачем.** Точка подстановки ровно одна. Jinja2 добавил бы зависимость, новый
синтаксис и риск случайного экранирования — ради одной операции `str.replace`.
Шаблон остаётся валидным HTML: его можно открыть в браузере и править в любом
редакторе.

**Цена.** Логика витрины (поиск, фильтры, подсветка) живёт в JavaScript внутри
шаблона и не покрыта Python-тестами. Пока страница не развивается функционально,
это приемлемо; если появится нетривиальное поведение, понадобятся браузерные
тесты.

### Ноль runtime-зависимостей

Пакет использует только стандартную библиотеку: `json`, `csv`, `dataclasses`,
`argparse`, `importlib.resources`, `pathlib`.

**Зачем.** Инструмент запускается в любом окружении с Python 3.11+ — в минимальном
контейнере CI, на машине контрибьютора, из другого проекта. Нет цепочки
обновлений и уязвимостей в транзитивных зависимостях.

**Цена.** CLI на `argparse` многословнее, чем на Typer или Click. Для четырёх
команд разница не окупает зависимость.

### Валидация — реестр правил, а не один большой проход

Каждое правило — чистая функция `(Glossary, ValidationConfig) -> Iterator[Issue]`,
зарегистрированная в `RULES`.

**Зачем.** Новая проверка добавляется одной функцией и одной строкой; каждое
правило тестируется изолированно; отчёт можно фильтровать и агрегировать по
именам правил.

**Цена.** Каждое правило проходит по всем карточкам заново — десять проходов
вместо одного. На 581 карточке это доли миллисекунды; при росте на порядок
имеет смысл сгруппировать покарточные правила в один проход, сохранив внешний
контракт.

### Ошибки и предупреждения разделены

Ошибки ломают CI, предупреждения — нет.

**Зачем.** Данные достались проекту в готовом виде и содержат замечания, которые
нельзя устранить за один коммит. Если бы каждое замечание было ошибкой, ветка
`main` была бы красной с первого дня, и проверка перестала бы что-либо значить.

Механизм ужесточения: правило вводится как предупреждение → замечания
устраняются → правило переводится в ошибки. Порог движения контролирует храповик
`tests/quality_baseline.json`.

## Текущий технический долг

| Что | Почему это долг | Когда разбирать |
| --- | --- | --- |
| 74 карточки ссылаются на корень `docs.python.org/3/` | Ссылка не помогает читателю | Этап правки контента |
| 14 имён встречаются дважды в разных разделах | Возможные дубликаты или неудачные имена | Этап правки контента |
| 5 маркеров версии без `+` (`3.5`, `3.9`) | Неконсистентная запись | Этап правки контента |
| Раздел `Файлы и I_O` | Похоже на артефакт экранирования `I/O` | Этап правки контента |
| Смешанные алфавиты в `id` (латиница и кириллица) | Не дефект, но конвенция не сформулирована | Требует решения |
| JavaScript витрины не покрыт тестами | Регрессия в поиске или фильтрах пройдёт незамеченной | При развитии витрины |
| Схема данных плоская, нет связей между карточками | Ограничивает «см. также» и графовую навигацию | При росте требований |

## Возможные направления

- **Синхронизация со Stepik-Python-Grader.** Сейчас данные переносятся вручную.
  Формат `data/glossary.json` и JSON-экспорт задуманы как контракт для будущей
  автоматической выгрузки.
- **Новые форматы экспорта.** Anki-колода, JSON Lines для индексации, вложения
  для LLM-ассистента. Реестр экспортёров рассчитан на такое расширение.
- **Мультиязычность.** Потребует несовместимого изменения схемы: `description`
  и остальные тексты станут словарями по языковым кодам. Поле `schema_version`
  добавлено заранее именно ради такого перехода.
