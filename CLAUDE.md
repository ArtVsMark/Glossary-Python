# Правила работы в этом репозитории

## Что это за проект

Витрина и инструменты вокруг глоссария Python. Живой глоссарий ведётся как база
знаний в проекте Stepik-Python-Grader; сюда данные попадают выгрузкой.

## Незыблемое правило

**У содержания один хозяин, и он не здесь.** Карточки ведутся в базе знаний
`ArtVsMark/Stepik-Python-Grader`. В этом репозитории оба файла с данными —
производные и вручную не правятся:

```
Stepik-Python-Grader ──► scripts/import_from_grader.py ──► data/glossary.json
                                                                  │
                                                      glossary build
                                                                  ▼
                                                      python_glossary.html
```

`data/glossary.json` — **снимок**, а не источник истины. Правка карточки здесь
живёт до первой выгрузки и молча исчезает; спор о том, чья версия верна, решать
некому. Поэтому обратного потока нет: замечание к содержанию едет в источник
письмом, а не правкой на месте.

```bash
make import SOURCE=/путь/к/Stepik-Python-Grader   # перечитать карточки
make validate && make build                       # проверить и пересобрать
make objections                                   # что предъявить источнику
```

Коммитятся оба файла — снимок и витрина. CI проверяет синхронность витрины со
снимком и отклоняет расхождение.

## Команды

```bash
make check      # полный набор проверок, тот же, что в CI
make format     # ruff: автоформатирование и автоисправления
make validate   # правила качества данных
make objections # замечания к содержанию — письмом в источник
make completeness # чего в глоссарии нет вовсе (эталон — сам Python)
make exclusives # два «только» об одном предмете в одном документе
make defaults   # умолчания окружения: кодировка, часовой пояс
make outcomes   # у каждой точки входа есть третий исход
make attribution # имена авторов коммитов ветки — из списка
make journal    # запись журнала едет вместе с изменением
make deadlines  # у процесса и у работы конвейера назван срок
make links      # ссылки документации разрешаются в файлы дерева
make build      # пересборка витрины
make test       # pytest
```

Прямые вызовы: `python -m glossary {validate,build,export,stats,objections,completeness,inventory}`.

## Роли

При работе над содержанием, визуалом, сборкой страницы, схемой данных и
возражениями грейдеру отвечай от лица релевантных ролей, помечая каждую.
Полный состав, приёмка новой роли и матрица подключения — канонически
в [`docs/agent/roles.md`](docs/agent/roles.md); здесь только триггер.

## Конвенции кода

- Python 3.11+, `from __future__ import annotations` в каждом модуле.
- Аннотации типов обязательны, mypy в строгом режиме проходит без исключений.
- Docstring на модуль, публичный класс и публичную функцию; стиль Google,
  на русском языке.
- Комментарий объясняет «почему». «Что» должно быть понятно из кода.
- Строка — до 90 символов; форматирует ruff, вручную не выравнивать.
- Новое поведение — с тестом. Покрытие не ниже 90 %.

## Чего не делать

- Не править `python_glossary.html` и `data/glossary.json` напрямую: оба
  производные. Содержание меняется в источнике, сюда приезжает импортом.
- Не менять содержимое карточек в рамках инфраструктурных задач — контент
  и инструменты развиваются отдельными изменениями.
- Не добавлять runtime-зависимости в пакет без явного обсуждения: ноль
  зависимостей — осознанное архитектурное решение (см. `docs/architecture.md`).
- Не писать числа в документации руками: только внутри маркера и только
  сборкой (`make facts`). Значки и `facts.json` в `main` не коммитятся.
  <!--предмет:числа в документации-->
- Не дописывать строку в `CHANGELOG.md` руками — только фрагментом
  в `changelog.d/`: общий файл конфликтует на каждом параллельном изменении.
  <!--предмет:записи журнала-->
- Не заводить роль, которая только соглашается: нет своего возражения
  конкретной роли — это профиль существующей.
  <!--предмет:нет-->
- Не проверять ссылку вхождением её адреса в текст: подстрока находится в
  подписи, и `[docs/architecture.md](никуда.md)` проходит такую проверку
  зелёной. Ссылка ищется разметкой — этим занят `scripts/check_links.py`.
- Не поднимать планку в `tests/quality_baseline.json` и `tests/completeness_floor.json`.
  Обе движутся только вниз.
  <!--предмет:направление планок качества данных-->
- Не писать версию пакета вторым местом: она объявлена в `pyproject.toml`,
  `__version__` выводится из метаданных дистрибутива. Литерал в исходниках
  ловит `tests/test_version.py`.
- Не считать заполненность обеих половин переводом: русский текст, скопированный
  в английское поле, проходит проверку ключей зелёным. Перевод проверяется
  свойством самого текста — этим занято правило `language-script`.
- Не называть полноту глоссария покрытием: покрытие — про тесты, и одно имя
  на два числа уже однажды затёрло чужой значок молча.
- Не читать зелёный набор на подделках как утверждение о дереве: подделки
  показывают, что разбор устроен верно, и молчат о том, что разбирают.
  У гейта две половины, и живая объявляется маркером `pytest.mark.live_surface`;
  её отсутствие — находка `tests/test_live_surface.py`.
- Не переводить правило валидации в уровень «ошибка», пока данные ему
  не соответствуют полностью — иначе `main` станет красной.
- Не писать «только» и «единственный» в нормативном документе, не назвав
  предмет маркером: утверждение связывает документ целиком, а пишется внутри
  раздела, где видна одна плоскость.
  <!--предмет:нет-->
- Не отвечать «механизма нет» про требование целиком: сначала разложить его
  надвое. Разбор всех 35 таких ответов за один заход нашёл два устаревших
  вердикта и одну машинную половину, лежавшую в том же файле.

## Каталог правил

Проект — потребитель каталога
[ArtVsMark/Engineering-Incidents-Playbook](https://github.com/ArtVsMark/Engineering-Incidents-Playbook).

- Ответ по каждому правилу — `.rules/bindings.json`. Статусы: `active`
  (обязательны `mechanism` и `where`), `rejected` и `not-applicable`
  (обязательно `why`), `unreviewed` — честное «ещё не смотрели».
- Правило, родившееся здесь, едет в каталог через `.rules/proposals.json`
  как **инцидент**, а не готовая запись. Номер присваивает каталог.
- Набор подключения собран командой каталога `onboard_consumer.py`. Файлы
  `.rules/*.json` и `rules-inbox.yml` целиком руками не переписываются;
  осознанно меняются только ответы по правилам, расписание и тег.
  <!--предмет:набор подключения к каталогу-->
- Новое правило без механизма — обещание. Либо гейт, либо явная пометка,
  что механизма нет и почему.
- Форму ответа держит `tests/test_rules_bindings.py`: адрес механизма обязан
  разрешаться в существующий файл, у каждого `none` названа причина.
- Причины у `none` мало: поле `machine_half` говорит, что из требования следует
  из данных целиком и почему оно не построено — половины нет, нашла бы пустоту
  или очередь. Ответ про всё требование сразу звучит как «требует суждения» и
  потому не перепроверяется годами.
- Вердикт «предмета нет», опровергаемый одной командой поиска, несёт свой
  рецепт опровержения в поле `refuted_by`, и набор его исполняет. Нашли
  опровержение — отказ; не нашли — молчание: это разные ответы.
- Правил без механизма сейчас **<!--m:rules_none-->19<!--/m:rules_none-->**, потолок зафиксирован в том же тесте.
  Планка двигается только вниз — как и `tests/quality_baseline.json`.
  <!--предмет:потолок правил без механизма-->
- Незакрытая работа по правилам идёт впереди новой: пока есть `unreviewed`
  или правило без разбора, новые задачи не начинаются.

## Работа с GitHub

Транспорт — REST. Одна операция GraphQL стоит около трёхсот единиц часовой
квоты против одной у REST, поэтому работа, укладывающаяся по REST в проценты
бюджета, по GraphQL в час не помещается. Счётчик считает попытки, а не успехи:
сверх лимита запрос отбивается отказом и всё равно списывается — «добить
остаток» не выйдет (правило каталога 001).

Наружу ходят двое, и по-разному.

**Дерево** ходит из `scripts/automerge.py` и больше ниоткуда. Идентификатор
изменения читается по REST, а мутация — одна на изменение, ради операции, у
которой REST-эквивалента нет вовсе.
<!--предмет:точка выхода из дерева-->

**Окно** ходит через MCP-сервер GitHub, транспорт которого мы не выбираем.
Различается он по форме ответа: курсоры `pageInfo`/`endCursor` — GraphQL,
числовая страница `page`/`perPage` — REST.

Список операций, идущих по GraphQL, закрытый, и у каждой названа причина:

| Операция | Кто зовёт | Почему не REST |
| --- | --- | --- |
| `enablePullRequestAutoMerge` | дерево | включения авто-мержа в REST нет вовсе — правило 001 называет эту операцию первой в своём закрытом списке исключений. Вызывается один раз на изменение и не опрашивает ничего: сливает площадка |
| `pull_request_read` / `get_review_comments` | окно | треда ревью в REST нет как понятия: он отдаёт плоские комментарии с `in_reply_to_id`, без группировки и без признака «отправлено Claude» |
| `list_issues` | окно | в REST операция есть, но сервер даёт перечисление задач только так. Правило исполняется сужением: задачу читают по номеру через `issue_read`, а перечисление зовут, лишь когда номер неизвестен |

Замер, с которого список начался: в одной сессии окно вызвало обе свои
операции, пока ответ по правилу 001 утверждал, что предмета у него нет вовсе.
Утверждение было верно про дерево и неверно про окно — а живёт правило в обоих.

Форму списка держат два набора: `tests/test_github_transport.py` требует
причины у каждой строки, `tests/test_automerge.py` — чтобы обращений к GraphQL
в дереве было ровно одно. Что причина верна, машина не проверяет: это суждение
о том, чего REST не умеет.

Согласие на слияние выражается **снятием черновика**: изменение, вышедшее из
черновика, ставится в очередь площадки и уезжает в `main`, как только
обязательные проверки позеленели. Ревью здесь не ждут — это осознанный выбор, а
не недосмотр.
<!--предмет:согласие на слияние-->

**Дописывать в открытое изменение нельзя — оно уедет из-под руки.** Замер
7 сентября: изменение #30 позеленело и слилось через четыре минуты после
открытия, пока в ту же ветку готовился второй коммит. Он остался без изменения
вовсе — ветка ушла вперёд `main`, а PR был уже закрыт. Правило работы простое:
одна ветка — одно изменение, следующая работа начинается от свежего `main`.
Черновик задерживает так же надёжно, как метка `hold`, и стоит дешевле.

Настройка репозитория «Allow auto-merge» живёт вне дерева, и включить её из
прогона нельзя: у токена прогона нет прав на настройки. Пока она выключена,
мутация отвечает отказом, и прогон печатает это словами.

## Что проект отдаёт наружу

Четыре файла в ветке `badges`, все с общей шапкой из `glossary.contracts`
(строковая `schema`, `schema_of`, `producer`, `source`, `generated_at`).
Издатель считает, потребитель читает обычным HTTP — правило каталога 174.

| Файл | Отвечает на вопрос |
| --- | --- |
| `facts.json` | Сколько всего: карточки, разделы, замечания, состав ответа каталогу |
| `objections.json` | Какие карточки **неверны** — правило, область, полный список |
| `completeness-report.json` | Каких карточек **нет** — эталон полноты сам Python |
| `whatsnew.json` | Что **появилось в языке** между версиями и не описано |

Три последних адресованы источнику: содержание правится там. Правило валидации
здесь — это форма возражения, а не запрет.

Границы измерения названы в самих отчётах, а не подразумеваются: интроспекция
видит объекты, а не текст (синтаксис, устаревания и удаления не измеряются), а
разность версий говорит «появилось в инвентаре», а не «появилось в языке».
